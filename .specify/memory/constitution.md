# pythonSDD 專案憲章

## Core Principles

### I. 可讀性優先，循序抽象

每個函式或類別 MUST 有清楚且單一的責任；命名 MUST 能直接表達用途；註解 MUST
解釋不容易從程式碼看出的原因、規則或遊戲設計決定。新增抽象層、設計模式或第三方
套件前 MUST 先說明它解決的具體問題。程式碼 MUST 以目前開發者能閱讀、修改與除錯為
優先，只有在重複、複雜度或功能邊界已清楚時才逐步重構。

理由：目前專案以單檔 Python 與直接命名的函式、類別累積功能；維持這種可追蹤的結構，
能讓每次學習與修改都可驗證，避免為了形式上的架構而增加理解成本。

### II. 遊戲物件封裝狀態與行為

每個遊戲物件 MUST 將自身的資料與直接相關的行為放在同一個類別中。`Brick`、
`Paddle`、`Ball`、動畫物件等類別 MUST 負責自己的狀態更新或繪製；跨物件的規則，例如
碰撞、計分、生命與勝負判定，MUST 由命名清楚的函式集中協調。全域常數 MAY 用於視窗、
顏色、速度與規則設定，但遊戲進行中的可變狀態 MUST 避免以無關的全域變數散落管理。

理由：目前程式已能以類別表示磚塊、底板、球與動畫；延續這個邊界可讓新功能容易定位，
也能降低修改一項效果時意外影響其他物件的風險。

### III. 小步驟開發，每項行為都可驗證

每次變更 MUST 聚焦一個可描述的行為，例如移動、反彈、磚塊耐久度、特殊效果或重新
開始。完成變更後 MUST 先通過 Python 語法檢查，再以可重現的操作或測試驗證正常流程與
至少一個邊界情況；涉及純邏輯的函式 SHOULD 優先設計成不依賴畫面的形式，以便日後加入
自動化測試。若行為改變，提交內容 MUST 同步說明驗證方式與已知限制。

理由：目前功能是從基礎視窗逐步增加到底板、球、碰撞、特效、生命與勝利狀態；小步驟
驗證能保留這條學習軌跡，並在遊戲迴圈變複雜後仍能快速定位問題。

### IV. 遊戲迴圈順序與狀態轉移明確

主迴圈 MUST 維持明確順序：限制幀率、處理事件、讀取輸入、更新物件、處理碰撞與規則、
更新動畫、繪製畫面、顯示畫面。每個可結束或重置的狀態 MUST 有明確條件與轉移方式，
至少涵蓋進行中、球未發射、球遺失、遊戲結束與勝利等情況。新增碰撞或計時規則時 MUST
處理邊界位置、重複觸發、重置後的初始值，以及多球或多物件同時存在的情況。

理由：目前遊戲已使用固定 FPS、事件處理、碰撞、生命、遊戲結束與勝利畫面；把順序與
狀態寫成共同規則，可避免更新先後造成的穿透、重複計分或重置錯誤。

### V. 保持範圍適當與依賴簡單

功能 MUST 先滿足規格中的必要行為，再考慮延伸效果；未被需求、錯誤修正或可驗證的
學習目標支持的複雜度 MUST NOT 被加入。專案預設使用 Python 與 Pygame；新增依賴 MUST
記錄用途、版本與安裝方式，且不得以依賴取代能清楚寫出的基礎邏輯。無效匯入、重複程式
碼與已知的除錯輸出 MUST 在完成一項功能前清理，除非保留它們有明確理由。

理由：目前專案以 Pygame 完成完整的打磚塊遊戲，並透過直接的資料結構與函式表達規則；
控制依賴與範圍能讓重點留在 Python 基礎、遊戲邏輯與逐步改善品質。

## 技術與範圍限制

- 核心執行環境 MUST 以 Python 3.11 以上為基準，遊戲功能 MUST 以 Pygame 為主要視窗、
  輸入與繪圖函式庫；若改用其他技術，規格 MUST 說明原因、影響與遷移方式。
- 視窗尺寸、幀率、顏色與遊戲規則 MUST 集中在容易找到的設定區；物件類別 MUST 不得
  複製同一份規則常數。
- 使用者可見文字與教學註解得使用繁體中文；函式、類別與變數名稱 MUST 維持一致的英文
  命名風格，除非既有 API 或外部規格要求其他命名。
- 不得為了未使用的未來功能預先建立多層資料夾、框架或服務；當單檔已妨礙測試或理解時，
  才依責任邊界拆分模組。

## 開發流程與品質門檻

1. 變更開始前 MUST 以規格或簡短需求描述行為、輸入、輸出與不處理的範圍。
2. 實作 MUST 按可獨立執行的任務切分；每個任務完成後 MUST 保持程式可啟動，或明確標示
   尚未完成的暫存狀態。
3. 每次變更至少 MUST 執行語法檢查與一次手動遊戲流程驗證；碰撞、計分、生命、重置等
   純邏輯 SHOULD 附上可重複的案例，並在測試需求增加時建立自動化測試。
4. 除錯時 MUST 先重現問題，再以最小修正驗證原因；不得以刪除功能或忽略錯誤訊息作為
   通用修復方式。
5. 提交或交付前 MUST 檢查未使用匯入、明顯重複邏輯、邊界錯誤與啟動方式，並記錄已完成
   的驗證與仍存在的限制。

## Governance

本憲章是本專案的開發約束；規格、計畫、任務與程式碼不得故意違反它。若需求確實需要
例外，提出變更時 MUST 同時記錄例外範圍、技術理由、風險與回復或遷移方式，並在實作前
取得專案負責人同意。

憲章修訂流程如下：

1. 先在規格或變更說明中描述修訂動機與受影響的原則。
2. 檢查現有程式、範本、測試與開發流程，列出需要同步調整的內容。
3. 更新本檔案頂端的 Sync Impact Report、版本與日期，再以本憲章的品質門檻驗證。
4. 任何受新規則影響的既有功能 MUST 有遷移說明；未完成遷移前，不得宣稱整個專案符合
   新版憲章。

版本遵循語意化版本：MAJOR 代表移除或重新定義既有不可妥協原則；MINOR 代表新增原則、
章節或實質擴充規則；PATCH 代表不改變治理意義的澄清、修正與文字整理。每次修訂 MUST
在交付或審查時確認版本、影響報告、日期格式與原則可驗證性一致。

Spec-kit 與 Git 交付流程另遵守以下規則：

1. 功能分支 MUST 使用 `.specify/scripts/powershell/create-new-feature.ps1` 或其等價的
   Spec-kit 產生流程建立，命名格式 MUST 為 `NNN-short-name`：三位以上的數字編號、
   小寫英數字與單一連字號；不得自行加上 `codex/` 或其他未經規範的前綴。功能分支與
   `specs/` 下對應的功能目錄 SHOULD 使用相同識別名稱，若不同 MUST 在計畫文件說明
   對應關係。
2. 功能分支完成後 MUST 推送至遠端並建立以 `main` 為 base 的 PR；PR MUST 說明對應的
   `spec.md`、`plan.md`、`tasks.md`、驗證結果與已知限制。未通過 code review、語法檢查、
   自動化測試與必要的手動驗證前，不得宣告可合併。
3. PR 合併後 MUST 先確認合併 commit 已存在於 `main`，再刪除遠端功能分支與本地功能
   分支；刪除前不得假設 PR 已合併。清理分支時 MUST 保留不屬於該功能的工作區變更。
4. Release MUST 從已合併且已驗證的 `main` 建立，並使用明確記錄的語意化版本 tag；沒有
   既有版本規範時，建立正式 Release 前 MUST 先確認版本號，不得從尚未合併的功能分支
   直接建立正式版本。
