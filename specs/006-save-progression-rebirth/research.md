# 研究與設計決策：持久化存檔、進度與重生戰役

**功能**：`006-save-progression-rebirth`

**研究日期**：2026-08-27

## 研究範圍與現況基線

- 目前 `air_defense` 已有 Ursina 3D 遊戲迴圈、`GameSession`、`WaveRuntime`、`WaveDirector`、單目標鎖定與地面遭遇流程。
- 目前 `WaveDirector` 與 `GameSession` 仍依賴固定 18 關；`main.py` 仍在 `E`／`G` 輸入、拾取／丟棄武器與戰鬥階段武器限制上負責協調。
- `entities.py` 尚無 RPG、多目標鎖定、陸地自動防禦、彈藥與回血狀態；`hud.py` 尚無五存檔、商店、重生與多鎖定顯示。
- 005 的規格、計畫與契約描述的是已合併的下降戰役基線；006 必須保留 005 的下降、混合戰鬥與撞擊處理，並明確取代其固定關卡與輸入相容規則。
- `requirements-game.txt` 只有既有的 `ursina==8.3.0`；純邏輯測試使用 Python 標準函式庫與 `unittest`。

## 決策

### D-001：使用版本化本機 JSON 存檔

**決策**：五個欄位各自保存一個結構版本（`schema_version`）為 1 的 JSON 檔案，預設放在使用者的
Windows 應用程式資料區；`SaveStore` 接受可替換的根目錄供測試使用。

**理由**：JSON 可檢視、可驗證、容易進行版本遷移，且符合「不可使用 pickle」與離線單機的
需求。將根目錄注入也能讓存檔測試不接觸真實使用者資料。

**替代方案**：pickle 會執行不安全的物件反序列化；SQLite 或雲端同步會增加依賴、部署與
範圍，現階段沒有必要。

### D-002：原子替換與損壞保留

**決策**：寫入時先在同一目錄建立暫存檔，完成 flush／fsync 後以原子替換取代目標檔案。
格式錯誤或未支援版本的原檔不得直接覆蓋，需保留原檔並回傳可顯示的恢復警告。

**理由**：程式中斷或部分寫入不能破壞一個存檔，也不能波及其他欄位；這是本機進度資料
最重要的安全邊界。

**替代方案**：直接覆寫較簡單，但可能留下截斷 JSON；只回傳空白資料而刪除原檔則會失去
診斷與恢復依據。

### D-003：A 與 a-b 關卡使用公式產生

**決策**：最大飛機數量永遠由 `A = 2 + rebirth_count` 推導；`LevelKey(a, b)` 與
`LevelPlan` 依數學規則生成。006 Profile 流程不保留 18 關靜態表，也不在生成器加入 4 台
或 18 關上限；為維持 005 舊呼叫端，整數 `WaveDirector` 僅另存為明確隔離的相容適配器，
不得被新的 Profile 流程使用。

**理由**：公式能直接保證 `a<A` 不出現魔王、只有 `a==A` 進入魔王階段，並讓重生自然
擴充難度。固定資料表會再次引入規格明確要求移除的永久上限。

**替代方案**：以每次重生追加一張手寫關卡表會重複資料、難以驗證，也容易漏掉較大的 A；
若直接刪除 005 相容表，則會在本功能範圍外破壞尚未遷移的舊呼叫端，因此先以隔離適配器
保留，後續遷移完成後再移除。

### D-004：正常進度暫存，存檔只保存最近完成紀錄

**決策**：一次「開始遊戲」只執行一個小關；正常完成後在記憶體中移到下一個 `a-b`，
返回主選單。死亡、重新載入存檔與重生後回到 1-1；JSON 不保存未完成的 a-b 進度，
但保存最近一次成功完成的 `a-b` 紀錄供顯示／診斷，不能用來續關。

**理由**：這同時符合「每次一小關」與「不保存未完成 a-b 進度」的確認結果，也保留使用者
要求的安全進度摘要，並讓關卡仍可在
同次執行期間逐步推進。

**替代方案**：永久保存目前關卡會違反已確認的資料邊界；每次永遠從 1-1 且沒有暫存指標
則無法抵達較高 b 或目前 A 的最終小關。

### D-005：獎勵與重生使用一次性領域操作

**決策**：每次小關嘗試有唯一 `attempt_id` 與獎勵結算旗標。完成事件只結算一次；死亡
不發放獎勵；死亡後重玩是新的嘗試。重生操作在成功後立即清除資格並保存。

**理由**：遊戲迴圈、碰撞與 UI 回呼都可能重複通知，冪等操作必須位於規則層，而不
能只依賴控制器的單一路徑。

**替代方案**：只在 UI 端禁用按鈕無法防止過時事件；保存每個 a-b 的永久領取收據則
會重新引入被排除的關卡進度資料。

### D-006：永久 Profile 與 RunState 分離

**決策**：`SaveProfile` 只保存金幣、重生、升級、解鎖、資格與最近完成紀錄；`RunState`
保存 HP、城市、敵人、彈藥、砲塔、鎖定、冷卻、回血額度、目前 a-b 與戰鬥階段，
`SessionProgress` 保存非持久化的下一關指標。兩者只
透過明確的開始／結算操作交換資料；場景物件不得建立第二份可獨立修改的戰鬥紀錄表。

**理由**：可避免死亡、勝利或重生時誤清除永久資料，也符合現有分層與憲章對可變狀態
集中管理的要求。

**替代方案**：把 Profile 直接塞進 `config.py` 或將所有欄位放入 `GameSession`，會讓
設定、永久資料與本局狀態互相污染。

### D-007：新武器加入既有目標規則，不加入階段鎖

**決策**：所有已解鎖手持武器在三個戰鬥階段均可切換；射擊前由純規則函式驗證目標、
射程、冷卻與彈藥。多目標防空炮另使用多鎖定集合，解鎖後鎖定 2 個目標，目標數量升級
等級從 0 開始，第一次升級價格為 500，後續依 `500*(level+1)` 計算，硬上限為 6；單目標
防空炮保留現有單目標鎖定追蹤器。

**理由**：將可用性與目標合法性拆開，能移除舊的 `AIRSTRIKE`／`GROUND_COMBAT` 限制而
不讓武器攻擊錯誤敵人。

**替代方案**：複製一套新的戰鬥判定會造成單目標與多目標鎖定漂移；繼續使用階段白名單
則直接違反 006 需求。

### D-008：RPG 爆炸以唯一目標快照結算

**決策**：RPG 只以地面敵人為合法目標，並在爆炸瞬間建立地面敵人 ID 集合；同一爆炸內每個
ID 只結算一次傷害。爆炸半徑、傷害、冷卻與彈藥量都是集中管理的可調參數，飛機不得被 RPG
直接或以範圍傷害命中。

**理由**：一次爆炸可能同時收到多個碰撞回呼，先建立唯一集合可保證結果與回呼
順序無關。

**替代方案**：逐碰撞立即扣血會使同一敵人因多個碰撞體或重複事件受到多次傷害。

### D-009：陸地自動防禦使用固定位置與硬上限

**決策**：場景預先提供六個固定砲塔位置；商店以 600 金幣解鎖，解鎖後每個新小關自動
建立 1 台，容量升級價格為 `450*(level+1)`，每級增加 1 台，單次小關最多建立六台暫時
砲塔，不提供戰鬥中購買或任意放置。每台預設每小關 20 發、每次射擊冷卻 1.5 秒、每次命中
傷害 20，且只保有一個目標；目標選擇採最近距離後以穩定 ID 破同分。容量等級從 0 開始，
第一次升級價格為 450，後續依 `450*(level+1)` 計算。

**理由**：同時滿足可購買多台與效能安全，並避免玩家輸入或重複回呼無限建立實體。

**替代方案**：允許任意世界座標與無上限實體會使碰撞、更新與清理成本不可控；固定一台
則無法滿足多台防禦需求。

### D-010：回血採每小關總額度限制的有限緩回

**決策**：每個小關建立 `0.2 * effective_max_hp` 的自動回血總額度。受傷後等待 5 秒，
以每秒 2 HP 回復；每次週期最多使用剩餘額度，再次受傷只重新啟動計時與該週期上限，
不增加小關總額度。第一版不加入醫療包。

**理由**：提供明確回血機制，同時避免無條件立即補滿與戰鬥中永久無限制回復。

**替代方案**：持續回滿會削弱受傷代價；完全依賴小關結算回血則無法滿足戰鬥中回血需求。

### D-011：保留既有 Ursina 執行環境，不新增套件

**決策**：006 沿用現有 `ursina==8.3.0` 與資產替代行為；純規則模組不可匯入 Ursina，
新增存檔只使用標準函式庫。

**理由**：這是 004／005 已記錄並接受的執行環境例外，006 不需要擴大例外或改造整個視窗層。

**替代方案**：遷移到另一個引擎會把持久化與進度需求擴張成不相關的執行環境遷移。

**治理範圍**：例外僅限目前 `air_defense` 的視窗／場景轉接層與既有 Ursina 依賴；理由、
影響、風險與未來遷移路徑沿用 004／005 的治理備註。006 不新增框架、服務、素材
或其他專案的例外。

### D-012：商店購買使用唯一操作 ID

**決策**：純規則函式處理單次購買，`GameSession` 以唯一 `operation_id` 記錄目前商店
操作的結果。相同 ID 的回呼只回傳第一次結果；新的 ID 才代表玩家的新購買，不把
操作紀錄寫入永久存檔。

**理由**：避免 UI 重複回呼洗掉金幣，同時不阻止玩家有意購買多個升級等級。

### D-013：選檔滑鼠路由與刪除二次確認

**決策**：`SAVE_SELECT` 的五個欄位以 Ursina `Button` 提供滑鼠點擊，並由 `main.py` 保留
`left mouse down` 的 hover 路由作為輸入後端的直接備援。每個非空欄位有獨立刪除按鈕；第一次
點擊只記錄暫時的 `pending_delete_slot`，第二次點擊「確認刪除」才呼叫
`GameSession.delete_save_slot()`。確認前可取消，空白欄位的刪除按鈕停用，成功或失敗後重新
列出五個欄位。

**理由**：選檔是啟動流程的第一個互動，不能只依賴可能未被視窗輸入橋接送達的按鈕回呼；
直接 hover 路由能讓滑鼠事件仍可到達流程層。刪除是不可逆的本機資料操作，二次確認與精確
欄位 API 可避免誤刪、重複回呼與跨欄位影響。

**替代方案**：只支援數字鍵會讓滑鼠使用者無法完成必要流程；一次點擊立即刪除會增加誤刪風險；
在主選單或戰鬥畫面提供刪除則會模糊目前選定 Profile 與五欄位的資料邊界。

### D-014：RPG 清除後以 RunState 聚合遭遇重試小關結算

**決策**：RPG 爆炸先建立唯一地面敵人快照並更新 `GroundEncounter` 的批次清除帳本，
再呼叫與其他傷害來源共用的整體小關清除判定。Profile 流程以 `RunState.ground_encounter`
作為聚合遭遇的權威來源；控制器的場景遭遇參照只作為快取，短暫為空或不同步時仍必須能
完成合法的最後一批敵人結算。

**理由**：多目標爆炸可能在單一輸入回呼中同時擊倒整批敵人；若只在一般地面更新週期
依賴控制器參照，視覺清理與領域更新的先後可能讓最後一次結算被漏掉，玩家會看到敵人已
消失但小關仍停留在戰鬥狀態。以 RunState 聚合資料重試可保留飛機、掉落與遭遇的完整條件，
並維持金幣結算的冪等性。

**替代方案**：讓 RPG 自行直接切換主選單會繞過所有飛機／掉落條件；只檢查視覺場景參照
則無法保證資料與畫面一致。

## 未保留的未決問題

本次研究已使用需求與先前確認的選擇解決所有會阻塞階段 1 設計的問題；沒有留下需求澄清
項目。平衡數值仍集中於單一設定資料結構，實作時可透過測試調整，
不改變資料模型與流程契約。
